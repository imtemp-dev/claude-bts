## Independent map

Written before opening `docs/research/pstack-lessons.md`.

### 1. What each system is

- pstack is prose only: about forty skills, twenty-four one-principle skills and twenty-three playbooks routed by `/poteto-mode`; no binary, no hooks, and the only state is a hand-written TSV decision log and a model-role rule file. Enforcement is instruction-following plus two small scripts (`check-plan.mjs`, `watch-pr`). **[read pstack/README.md:53, :112, :225; pstack/skills/poteto-mode/SKILL.md:122-150; run `find` over the copy]**
- pstack's multi-model stance is load-bearing: the default panel is opus 5.5 plus grok 4.7; arena runners, the cross-judge pool, interrogate reviewers and the how/why/reflect roles each take a model list from `pstack-models.mdc`. **[read pstack/README.md:43; pstack/skills/setup-pstack/SKILL.md:41-66; pstack/skills/arena/SKILL.md:17, :28; pstack/skills/poteto-mode/SKILL.md:96-100]**
- Under Claude Code, pstack's own adapter collapses that stance: `model` takes only `opus`, `sonnet`, `haiku`, `fable`; a grok or gpt slug maps to "omit model" (the session model); the grok default for code and swarm workers becomes `inherit-parent`. **[read pstack/docs/harness/claude-code.md:34-36, :45]** The arena cross-judge rule "never from the parent's family" cannot be met with Claude-only models, because families go by prefix (`claude-*`), so the judge seat is skipped and the coordinator picks alone. **[read pstack/skills/arena/SKILL.md:17, :28 last clauses]**
- bts is a Go binary plus deployed templates (twenty-five skills, eleven agents, eight hooks, seven rules) that enforces completion in code: stop-hook gates, a convergence budget and a round cap, a findings ledger with stable ids, per-document hashes, recorded overrides and a decisions ledger. **[read README.md:147; internal/engine/gate_registry.go:18-223; internal/hook/stop.go:63-96, :120-209, :269-330]** `settings.yaml` separates enforced keys from `[advisory]` ones and says why the distinction matters. **[read templates/.bts/config/settings.yaml:5-26]**
- bts's independence thesis is context isolation, not model family: "Never verify your own output in the same context", one context per gate, and "a gate that spawns a second gate is the failure mode". **[read templates/.claude/rules/bts-verification-protocol.md:19-33]**
- bts has measured and removed fan-out layers: the simulate walkers plus validator and rebuttal agents, and the fork-that-spawns-an-agent shape. Numbers it records: the fork cost $12-30 and 40-56 minutes against $2.5 and 5 minutes for the walk; validators handed 10-28 findings wrote 80-110K output tokens and were abandoned at the 64K limit; polling was 62% of a 72-minute wall clock; the rebuttal changed the outcome in two of nine challenges. **[read templates/.claude/skills/bts-simulate/SKILL.md:30-37; templates/.claude/skills/bts-defend/SKILL.md:36-43; templates/.claude/agents/bts-simulator.md:26-33; run `git show -s 06d381e bc18c4e 1235217 3a09436`]**

### 2. The mechanics bts already has for running agents

A port has exactly these levers, and each has a different enforcement status.

1. **Agent-tool spawn from the orchestrator.** `bts-review` spawns three reviewers "in a single message", then a validator (sonnet) and a rebuttal; the model comes from the agent file's `model:` or from the Agent tool's `model` argument. **[read templates/.claude/skills/bts-review/SKILL.md:90-92, :134-137; templates/.claude/agents/bts-reviewer-validator.md:5]** This is the shape that is hook-observable.
2. **Fork-as-agent.** Skill frontmatter `context: fork` plus `agent: <name>` runs the fork as that agent with its tools, model and turn cap, and the skill forbids any nested spawn. verify, audit, simulate, defend and assess use it. **[read templates/.claude/skills/bts-verify/SKILL.md:10-12, :21-28; templates/.claude/skills/bts-assess/SKILL.md:7-10; settings.yaml:165-166]**
3. **Skill-level `model:` frontmatter.** cross-check and sync-check pin sonnet this way. **[read templates/.claude/skills/bts-cross-check/SKILL.md:11; templates/.claude/skills/bts-sync-check/SKILL.md:10]**
4. **The pre-tool-use hook** sees every Agent spawn (`subagent_type`, `prompt`, and a `model` field if present, since `ToolInput` is a free map) and can deny it. Today it only counts scenario and finding ids for the `simulator` and `defender` agent types, a path no shipped skill uses any more because both run as forks; the file says so itself. **[read internal/hook/pre_tool_use.go:33-44, :149-151, :177-181, :182-219; internal/hook/types.go:39]**
5. **`agents:` in settings.yaml is not applied by Go.** It is whitelisted as a free-form map by doctor and `doctor_drift` warns about an active `reviewer_security:` line; no other Go code reads it. **[read internal/cli/doctor_config.go:179; internal/cli/doctor_drift.go:19-34; run `grep -rn 'agents' internal/ --include='*.go'`]** So for Agent-tool spawns the key is advisory (the skill reads it and passes `model`), and for fork-as-agent skills it is inert: the agent file's frontmatter wins and nothing rewrites it. `settings.yaml:165-166` says the keys override the agent file; no mechanism does that. **[inferred from the grep]**
6. **Metrics.** Subagent start and stop events carry recipe id and phase; `bts stats` reports per-session model, tokens and cost; the pricing table knows the opus, sonnet and haiku 4 prefixes only. Model is recorded per session, not per spawned agent. **[read internal/hook/subagent.go:82-93; internal/cli/stats.go:138, :293; internal/metrics/pricing.go:27-31; internal/metrics/metrics.go:25-50]**
7. **`bts update` can retire a template file and prune dead settings keys**, so a port that adds or replaces an agent has a clean deployment path. **[read internal/cli/update.go:40-62, :143-149, :183-212]**

### 3. pstack mechanisms worth porting, where they land, and how under the constraints

**A. Independent candidate generation in `/bts-architect` (the operator's example).**

- Today bts-architect Step 1 has the orchestrator itself propose two to four alternatives in the main context; Step 2 debates them as three personas played sequentially by the same context; Step 3 adjudicates on six dimensions; Step 4 writes the `<!-- architect-decision -->` block. **[read templates/.claude/skills/bts-architect/SKILL.md:37-69, :73-85, :87-97, :99-121; templates/.claude/skills/bts-debate/SKILL.md:21; templates/.claude/skills/bts-adjudicate/SKILL.md:28-82]**
- pstack's arena fans N runners out, each in its own output location, under one shared prompt that forbids hedging toward a middle; a read-only judge scores against a rubric the runners never see; the coordinator reads every candidate, picks a base, grafts the best parts of the losers, and treats convergence and wild divergence as signals. **[read pstack/skills/arena/SKILL.md:13-18, :22, :28, :32-40; pstack/skills/architect/references/runner-prompt.md:20]**
- Landing: Step 1 becomes a fan-out of N Agent spawns in one message (the bts-review shape), each writing `alternatives/{name}.md` under the recipe directory; the hook allows `.bts/` writes during spec phases. **[read internal/hook/pre_tool_use.go:67-70]** Runner inputs are `scope.md`, `domain.md`, the research doc's `## Official Guidance`, and `project-map.md`. The alternative keeps bts's shape (name, basis, node list, invariant ownership map, YAGNI check) **[read bts-architect/SKILL.md:46-69]** plus one pstack addition worth taking: a short "Usage (caller's view)" section with two or three call sites, which is what makes interface depth judgeable. **[read pstack/skills/architect/references/rationale-template.md:9-11]**
- Steps 2 to 4 stay. The decision block is machine-checked for `Selected:`, `Basis:` and `Invariant ownership:` by regex, so its shape must not change; an `Adopted from:` line (pstack's graft) can be added inside the block without touching the checker. **[read internal/engine/architect_decision_checker.go:19-25, :43-120; inferred for the added line]**
- Under the constraints: runners are opus x2 with structurally different seeds (one forced to the official pattern, which bts already mandates; one forced to the smallest surface) plus an optional sonnet x1. Diversity comes from the seed, not the family. **[read bts-architect/SKILL.md:39-44]** The judge is one read-only spawn that neither generated nor will pick. That is Fable's one role: once per recipe, bounded input, a scored table as output, with an explicit fallback to opus when the spawn is refused (pstack's rejected-slug rule). **[read pstack/skills/poteto-mode/SKILL.md:98; pstack/skills/arena/SKILL.md:28]** The orchestrator then picks per arena Phase D and treats disagreement with the judge as the signal. **[read pstack/skills/arena/SKILL.md:32]**
- Cost: N+1 spawns once per recipe. bts's own indicator targets at most one architect invocation per recipe, so the addition is bounded. **[read docs/bts-flow-metrics.md:46-58]** In exchange Step 1's generation leaves the orchestrator's context. No polling loop: spawn all in one message and wait for the notifications, exactly as bts-review does. This is not the fork-spawns-agent shape bts removed.
- Enforcement fit: the hook can count runner spawns per recipe and refuse more than N, check each runner's `model` against a declared list, and `bts verify wireframe.md` can require at least two `alternatives/*.md` files when `Selected:` is not `single-path`. Nothing in Go reads `alternatives/` today. **[run `grep -rn alternatives internal/ --include='*.go'` (empty)]**

**B. pstack's design red flags as a screen for the judge and for adjudicate.** Shallow module, information leakage, temporal decomposition, pass-through method, split ownership, two ways to do one task, importable internals, hand-synced list. **[read pstack/skills/architect/references/design-red-flags.md]** Two already exist as bts gates: split ownership is the invariant single-owner check, and the hand-synced list is the Derived-state rule in domain.md. **[read internal/engine/gate_registry.go:235-240; templates/.claude/skills/bts-domain-model/SKILL.md:86-99]** The other six are missing from adjudicate's "Over-engineering" and "Blind spots" dimensions. **[read bts-adjudicate/SKILL.md:53-58, :78-82]** Landing: a references file under `bts-architect/` and one line each in adjudicate 2d and 2f. Advisory, zero spawns.

**C. Convergence as a signal.** When independent candidates converge, pstack ships the consensus with no graft; wild divergence means the frame was under-specified. **[read pstack/skills/arena/SKILL.md:40]** bts runs the debate unconditionally. **[read bts-architect/SKILL.md:73-75]** Landing: an optional rule that convergent runners collapse the debate to one round (the fix recipe already uses one round). **[read settings.yaml:144-145]** A cost lever to measure, not assume.

**D. "A finding survives only when a run proves it."** **[read pstack/skills/interrogate/SKILL.md:9, :17-23]** bts already has this for specs as `Opens-with:` and falsifiers. **[read bts-verification-protocol.md:77-99]** The gap is code mode: reviewers have Read, Grep and Glob only, no Bash, so a code-phase critical finding is argued rather than run. **[read templates/.claude/agents/bts-reviewer-quality.md:5]** Landing: in bts-review full mode a critical finding against code must carry a command and its output or be downgraded, mirroring the deferred-minor contract; a Go check on `review.md` can enforce the shape. That is a prompt contract change plus a checker, not a new agent. Measured caution: bts's rebuttal round changed the outcome in two of nine, so strengthening the prosecution with runs is cheaper than adding more defense. **[read bts-defend/SKILL.md:41-42]**

**E. Reflect and eval as a developer-side loop for bts itself, not as templates.** pstack's reflect runs three lenses over the transcript, then a synthesizer sorts findings into Accepted, Rejected and Backlog, and moves anything a lint or script could enforce to Backlog. **[read pstack/skills/reflect/SKILL.md:23-49; pstack/skills/reflect/references/synthesizer.md:13-22]** Its eval playbook blinds the candidates. **[read pstack/skills/poteto-mode/playbooks/eval.md:5-13]** bts's "measure:" commits show the author doing this by hand. **[run `git log --oneline -60`]** Landing: `.claude/skills/` in the claude-bts repository as dev tooling, never under `internal/template/`. Models: opus for the judgment lens and synthesizer, sonnet for the tooling lens, which is pstack's own split. **[read pstack/skills/reflect/SKILL.md:29-33]**

**F. Model role lines as configuration.** pstack gives each role a model and each panel a list. **[read pstack/skills/setup-pstack/SKILL.md:41-66]** bts's `agents:` map is the same idea, advisory and unapplied (mechanics 5). Landing: keep `agents:`, add list-valued keys for the arena (runners, judge), and make the pre-tool-use hook read them for Agent-tool spawns so they become enforced; document that fork-as-agent skills take their model from the agent file. Do not advertise an override the binary does not apply.

- **swarm and the ten-lane live verification.** This is the fan-out shape bts measured and removed; pstack hard-codes "Ten lanes" in its plan checker and depends on Cursor cloud agents. **[read pstack/skills/swarm/SKILL.md:21-27; pstack/skills/poteto-mode/playbooks/multi-phase-plan.md:13, :100-111; pstack/skills/poteto-mode/scripts/check-plan.mjs:7, :158-161]**
- **Validator-and-rebuttal per finding batch.** pstack's interrogate keeps it as adversaries per worktree; bts replaced it with one defender pass after the round is logged. **[read bts-defend/SKILL.md:28-43]**
- **The twenty-four principle skills and the poteto-mode trigger list.** bts encodes the same lessons structurally, and pstack's own meta-principle says a structural fix makes the instruction a symptom. **[read settings.yaml:16-25; pstack/skills/principle-encode-lessons-in-structure/SKILL.md:9-11]**
- **show-me-your-work TSV.** bts already has `changelog.jsonl`, `findings.jsonl`, `decisions.jsonl` and `verify-log.jsonl`, written by the binary; a hand-written log is weaker. **[read templates/.claude/rules/bts-schema.md:111-245; bts-verification-protocol.md:374-405]**
- **babysit, shipping, autopilot, orchestrate, opening-a-pr.** PR lifecycle on Cursor cloud agents, outside bts's spec-to-code scope. The absence of any PR step in bts is noted under Missing.
- **The architect's type-sketch output into `draft.md`.** pstack's architect produces types, signatures and `not implemented` bodies. **[read pstack/skills/architect/SKILL.md:9, :77-79; runner-prompt.md:13]** bts excludes signatures from the blueprint on measured grounds (section length and finding count correlate at r=+0.95). **[read templates/.claude/rules/bts-level-criteria.md:57-62; templates/.claude/skills/bts-recipe-blueprint/SKILL.md:699-705; docs/bts-flow-metrics.md:287-292]** Sketches may live in `alternatives/*.md`, which the verify loop never reads, but must not enter `draft.md`.
- **Model-slug fallback ladders and per-role effort tiers.** Claude Code has four fixed model values and an `effort` field; bts already sets effort per skill frontmatter. **[read pstack/skills/poteto-mode/SKILL.md:98; settings.yaml:180-191]**
- **Comment Sicko, make-bot-ui, ketchup-video, statechart and TLA+, create-verification-skill as-is.** `bts graph paths` already gives deterministic path enumeration. **[read bts-verify/SKILL.md:43-50]**

### 5. Independence under Opus plus Sonnet, and where Fable goes

- pstack's independence claim is family diversity: "different models catch different real bugs", "a second opinion is the same prompt against a different model". **[read pstack/skills/blast-radius/SKILL.md:38; pstack/skills/poteto-mode/SKILL.md:100]** With Claude-only models the family rule is unsatisfiable, and pstack's own adapter degrades its seats to the session model.
- bts's measurements show that same-model, different-context runs already disagree substantially: consecutive rounds on a byte-identical document disagreed by two criticals and nine majors, and rounds after no edit averaged 8.9 new findings. **[read settings.yaml:75-81; bts-verification-protocol.md:227-236]** So two independent Opus contexts are not one sample; within-model variance is large enough to yield distinct candidates. What family diversity would add is coverage of shared systematic blind spots, such as a framework fact both Claude models misremember, and bts mitigates that with the evidence policy (Context7, then official domains) rather than with a second family. **[read templates/.claude/rules/bts-evidence-policy.md:26-83]**
- Sonnet as a runner buys less diversity than a second Opus runner with a different seed, and bts's own tiering note says design judgment is deep reasoning for the session model while sonnet is for pattern checks. **[read settings.yaml:158-166; run `git show -s 07ed271`]** Sonnet is a fine third candidate and a fine tooling lens, and a poor judge of decompositions.
- Fable's one role: the arena judge inside bts-architect. One spawn per recipe, read-only, at the decision that cascades into wireframe, draft and every verify round. Never inside the verify loop, which runs up to `verify.max_rounds` (6) times three instruments and would exhaust a rate-limited model. **[read settings.yaml:35-42, :183-186]**

### 2. A finding needs a falsifier: **change (keep the code half narrowed, drop the spec half)**

Code phase (line 38). Keep the direction, narrow the scope:

- "Each finding carries a command and its output" cannot apply to every finding. pstack's own interrogate drops style, naming and structure findings for exactly this reason. **[read pstack/skills/interrogate/SKILL.md:19]** bts-review's quality and architecture perspectives are mostly that class (naming, magic numbers, import direction). **[read templates/.claude/agents/bts-reviewer-quality.md:25-34; bts-reviewer-arch.md:16-36]** Require the run for **critical** findings in code mode; keep major as evidence-or-downgrade; leave minor and info alone.
- The reviewers have no Bash (`tools: Read, Grep, Glob`). **[read bts-reviewer-quality.md:5; bts-reviewer-security.md:5; bts-reviewer-arch.md:5]** Producing a command and its output means giving them Bash and an isolated place to run it; pstack puts each adversary in its own worktree. **[read pstack/skills/interrogate/SKILL.md:17]** That is a tooling change, not a prompt change, and it has side effects (a test run can write).
- Security is recall-bound by bts's own measurement, and the semantic flaws it names (authz bypass, state-dependent escalation) are the ones hardest to demonstrate with a command inside a review. **[read settings.yaml:160-161]** A run-proof requirement raises precision on exactly the findings where recall is the problem. Allow a concrete scenario (input, path, outcome) as the falsifier for security criticals, which is already the rebuttal agent's bar. **[read templates/.claude/agents/bts-reviewer-rebuttal.md:28-33]**
- "The orchestrator reruns it" adds one Bash turn per critical finding. Bounded and worth it; it is the same place the defend step already puts the orchestrator. **[read bts-defend/SKILL.md:100-120]**

Spec phase (line 39). Drop it as written. ## Recommended first slice

The smallest change that proves the idea is smaller than proposal 1 as written.

**Change:** `bts-architect` Step 1 only. Spawn two runner agents in one message (new agent file `templates/.claude/agents/bts-architect-runner.md`: tools Read, Grep, Glob, Write; `model: opus`; `maxTurns` bounded), each with the same brief and a different seed: one must apply the official pattern from research `## Official Guidance`, the other must minimise the public surface; both are told not to hedge toward a middle. Each writes `alternatives/{name}.md` in the existing shape (name, basis, node list, invariant ownership map, YAGNI check) plus a short "Usage (caller's view)" section. The orchestrator waits for the two notifications, then runs Steps 2 to 4 unchanged (debate, adjudicate, decision block). No judge, no Fable, no settings keys, no debate replacement. Optional Go line: `bts verify wireframe.md` reports a major when `Selected:` is not `single-path` and fewer than two `alternatives/*.md` exist.

What it proves: whether independent generation produces structurally different candidates and whether that changes the adjudicator's verdicts, before any of the costlier machinery (judge, tie-break, enforced model keys) is built.

**Measure, on the next three to five blueprint recipes against the existing baseline:**

| Signal | Source | Read as |
|---|---|---|
| Architect-phase cost and wall clock | `metrics.jsonl` events with `phase: architect`; `bts stats` | the price of the slice |
| Node-list overlap between the two alternatives | Jaccard over the node names in `alternatives/*.md`, by hand or a ten-line script | high overlap means the seeds are not producing diversity |
| Adjudicate verdicts: ACCEPT vs EXTEND, and extension count | `changelog.jsonl` adjudicate entries; `debates/*-followup` dirs | each avoided EXTEND saves a research pass and a debate |
| Indicator 2, re-decomposition count | `bts stats --indicators` | the downstream outcome the architect step exists for |
| Indicator 14, tier-5 (architect escalate) rate | `bts stats --indicators` | same, from the implement side |

Baseline the overlap metric first on any existing recipes that already carry `alternatives/` (same-context alternatives). If their overlap is already low and EXTEND rounds are rare, the arena has little to win and the next step (judge, Fable tie-break) should wait.

**Gate for the next slice:** add the fresh-context Opus judge and the Fable tie-break only if the first slice shows low overlap between candidates and at least one EXTEND round avoided, and record the judge-versus-orchestrator disagreement rate before deciding whether Fable sits in the judge seat or behind it.
